# Задание 2. Выбор и настройка мониторинга в системе

## 1. Мотивация

Мониторинг позволяет сделать систему "наблюдаемой". Это означает, что бизнес получает преимущества в виде:
- получения бизнес-инсайтов
- быстрое решение проблем и, как следствие, позитивная обратная связь от пользователей
- повышение надежности за счет информирования о проблемах
- выявление узких мест системы (с их последующим исправлением)
- повышение безопасности системы (отслеживание критических и необычных событий).

## 2. Выбор подхода к мониторингу

Предполагается комбинирование подходов.
Подходы USE и RED должны использоваться во всех backend-сервисах и выводить ключевые показатели метрик, характерные для API: утилизацию ресурсов, количество и процент ошибок, насыщенность, latency и трафик. Как правило, RED используется для мониторинга приложений, а USE для инфраструктуры.
Пример: для каждого бэкенд-сервиса будет использоваться RED-метрика, а на каждую ноду kubernetes будет установлен node-exporter для мониторинга состояния ноды.

## 3. Какие метрики и в каких частях системы отслеживать

1. MES API
- exceptions_total (количество ошибок)
- http_errors_total (ошибки HTTP 4xx/5xx) с ярлыками status, path
- timeout_requests_total (таймауты)
- http_requests_total (общее количество HTTP-запросов) с ярлыком method
- http_request_duration_seconds (гистограмма времени ответа или latency)
- process_cpu_seconds_total (использование CPU)
- process_resident_memory_bytes (использование RAM)

2. 3d files storage
- node_filesystem_avail_bytes (количество свободного места на диске) с ярлыком mountpoint

3. RabbitMQ
- rabbitmq_queue_messages_ready (сколько сообщений ожидают обработки) с ярлыком queue
- rabbitmq_queue_messages_unacknowledged (сколько сообщений в обработке) с ярлыком queue
- rabbitmq_queue_messages (всего сообщений) с ярлыком queue, плюс очередь Dead Letter Queue для мониторинга сообщений, которые не были обработаны успешно из-за ошибок потребителя
- rabbitmq_connections (активные подключения) с ярлыком queue

4. Redis
- used_memory (сколько памяти использует Redis)
- keyspace_hits и keyspace_misses (сколько раз ключи были найдены/не найдены)
- evicted_keys (количество удалённых ключей из-за нехватки памяти)
- instantaneous_ops_per_sec (число операций в секунду)

## 4. План действий

Необходимые задачи для внедрения Observability стека:
1. Добавить в инфраструктуру сервис OpenTelemetry Collector с конфигом для сбора трейсов (Tempo), метрик (Prometheus), логов (Loki)
2. Подключить в каждый микросервис OpenTelemetry SDK для экспорта трейсов, метрик и логов
3. Добавить в инфраструктуру сервис Prometheus для метрик с настройкой scrape target на otel-collector
4. Добавить в инфраструктуру сервис Tempo для трейсов с указанием его как exporter в otel-collector конфиге
5. Добавить в инфраструктуру сервис Loki для логов с указанием его как exporter в otel-collector конфиге
6. Добавить в инфраструктуру сервис Grafana для визуализации логов, трейсов и метрик
7. Добавить дашборды в Grafana (можно импортировать готовые)
8. Настроить алерты в Grafana (на критические события)
9. Протестировать, что трассировка работает, логи и метрики присутствуют
10. Написать сопроводительную документацию

## 5. Дополнительное задание

Добавление показателей насыщенности предполагает настройку пороговых значений, при которых будет возникать алерт, т.е. информирование о потенциальных проблемах. Предполагаемые показатели:
- Утилизация CPU%: `100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` - здесь можно настроить алерт на превышение 90%, чтобы сервис не занимал все процессорное время
- Использование RAM%: `1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)` - здесь можно настроить алерт на превышение 95%, чтобы не использовать swap
- 95 перцентиль задержки при выполнении запросов HTTP: `histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))` - тоже на определенное знаение, чтобы сервис отвечал требованиям по допустимой задержке ответа
