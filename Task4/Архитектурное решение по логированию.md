# Задание 4. Логирование

## 1. Какие логи нужно собирать

### INFO
Информационные сообщения помогают отслеживать нормальное функционирование системы, поэтому можно логировать такие действия как:
- изменение статуса заказа с сопутствующими атрибутами (номер заказа, время, идентификатор клиента)
- осуществление запросов к СУБД (SQL-запросы без подставленных значений параметров, время)
- вызов методов API у сервисов (метод, идентификатор пользователя, номер заказа, время) 
- загрузка файлов в хранилище (номер заказа, имя файла, размер, время).

### TRACE
Здесь предполагаются детализированные сообщения для трассировки кода и отслеживания шагов работы конкретного приложения. В случае с нашим проектом это может MES API:
- обработка файла 3D модели, которая может состоять из нескольких шагов (параметры модели, номер заказа, время события, время выполнения конкретного шага, общее время выполнения операции обработки).

### WARN
Возможные варианты:
- клиенты используют старую версию MES API.

### ERROR
Сообщения об ошибка, которые влияюи на выполнение системы, но не приводят к остановке. Это могут быть:
- таймауты операций в БД
- ошибка при попытке отправить запрос в сторонний сервис.

### DEBUG
То что не должно быть быть в производственной среде, предназначено для отладки и решения проблем. Например:
- логирование значений переменных, состояний объектов.

## 2. Мотивация
Добавление логирования в микросервисную инфраструктуру необходимо для:
1. Повышения надёжности: быстрое выявление и диагностика ошибок, инцидентов и нестабильного поведения сервисов.

2. Ускорения поиска и устранения проблем: меньше времени тратится на разбирательства при инцидентах, быстрее восстанавливается работоспособность системы.

3. Повышения прозрачности работы системы: логирование даёт понимание внутренних процессов, упрощает аудит действий пользователей и внутренних сервисов.

4. Улучшение показателей бизнеса: качественное логирование позволяет анализировать бизнес-процессы (например, сколько заказов успешно обработано) и оперативно замечать падение конверсии.

Логирование целесообразние внедрить в начале в центральной точке входа в приложение, т.е., в случае системы "Александрия" необходимо обеспечить наличие API Gateway. Далее уже остальные сервисы:
- MES API
- CRM API
- Shop API.

## 3. Предлагаемое решение

### Новые компоненты
1. Сервисы (бэкенд) должны логировать события с помощью биботек:
- Java (log4j)
- C# (Serilog)
2. Новый сервис OpenTelemetry Collector собирает логи от приложений через OLTP exporter
3. OpenTelemetry Collector складывает логи в новый сервис Loki (для хранения логов)
4. Новый сервис Grafana подключается к Loki для визуализации, поиска и анализа логов.

Новая схема модели C4 уровня контейнеров уже была дана в задании 3.

### Политика безопасности для логов
1. Не должны логировать чувствительные данные (пароли, данные платежных карт, личную информацию клиентов)
2. При наличии чувствительных данных - маскировать их
3. Обеспечить шифрование каналов для передачи логов
4. Доступ к Grafane только через выделенную учетную запись, ограничения по IP или внутренней сети.

### Политика хранения логов
1. Время хранения зависит от объемов трафика, на начальном этапе можно оставить 7 дней
2. Ожидаемый объем не более 100 Мб в сутки на сервис.

## 4. Необходимые мероприятия для превращения системы сбора логов в систему анализа логов
1. Стандартизация структуры лог-записи для каждого сервиса (чтобы каждый сервис писал логи в идентичном шаблонном формате)
2. В Grafana настроить дашборды, в которых выводить:
- количество ошибок по сервисам за сутки
- количество логов по уровням
- топ частых ошибок
3. Создать алерты на основе логов:
- если количество ошибок в сервисе за 5 минут превышает N
- если нет логов в сервисе в течение времени
- если в логах ошибка "Out of memory" (полезно для MES API).
