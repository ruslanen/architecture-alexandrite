# Задание 5. Кеширование

## 1. Какую часть системы имеет смысл закешировать
Имеет смысл закэшировать те части системы, которые выполняют запросы на чтение данных к СУБД, которые изменяются редко. Сюда можно отнести такие вещи, как:
- список активных заказов для операторов (дашборд MES)
- стоимость ранее рассчитанных изделий (MES)
- информация о клиентах(CRM)
- каталог готовых изделий и элементов конструктора украшений (Shop)
- статусы заказов для внешних API (Shop, CRM).

## 2. Мотивация
Предлагается внедрить кэширование, т.к. наблюдаются серьёзные проблемы с производительностью при росте нагрузки:
1. операторы жалуются на медленную загрузку дашбордов в MES
2. клиенты жалуются на долгие расчёты стоимости изделий
3. API для партнёров работает нестабильно под нагрузкой
4. увеличивается нагрузка на базы данных, что снижает стабильность всей системы.

Соответственно, кеширование необходимо, чтобы:
1. снизить нагрузку на базы данных и бэкенд-приложения
2. ускорить ответы для пользователей и внешних партнёров
3. повысить стабильность работы при росте числа заказов
4. улучшить пользовательский опыт и сократить количество жалоб.

## 3. Предлагаемое решение
Предлагается реализовать серверное кэширование, т.е. Cache-Aside, т.к, основная нагрузка возникает на бэкендах (MES, Shop, CRM) и базах данных. 

Паттерн Cache-Aside обеспечит, что приложение сначала сходит в кэш и если данные есть - вернет их, если нет - загрузит из БД и положит в кэш. Это достаточно гибкий и простой в реализации подход. Во многих средах (Java, C#) уже есть нативные библиотеки для имплементации паттерна. Данные о клиентах, результаты расчётов стоимости и статусы заказов изменяются не так часто. При необходимости кэш можно инвалидировать вручную.

Refresh-Ahead хорошо подходит для очень стабильных данных с высокой частотой запросов, а в нашем случае аказы и расчёты стоимости изменяются динамично и непредсказуемо. Write-Through усложняет архитектуру, а также записи происходят реже, чем чтение.

## 5. Стратегия инвалидации кеша

Предлагается вариант с инвалидацией кэша по ключу. В этом случае мы сами управляем кэшем.

| Метод инвалидации        | Преимущества                                     | Недостатки                                 |
|--------------------------|--------------------------------------------------|--------------------------------------------|
| **Программная**           | - Полный контроль над инвалидацией. <br> - Подходит для сложных бизнес-логик. <br> - Позволяет точно отслеживать, когда нужно обновить кешированные данные. | - Сложность в реализации и поддержке. <br> - Могут возникать ошибки при неправильной логике инвалидации. <br> - Необходимо тщательно следить за всеми зависимыми данными. |
| **По ключу**              | - Простота реализации. <br> - Инвалидация происходит напрямую через изменение данных (по ключу). <br> - Прямое соответствие между изменениями данных и обновлением кеша. | - Требуется отслеживание всех изменённых данных. <br> - Может быть сложно управлять маппингом ключей, особенно в больших системах. |
| **По времени**            | - Простота реализации. <br> - Применимо для данных, которые обновляются регулярно или через фиксированные интервалы времени. <br> - Не требует отслеживания изменений данных. | - Данные в кеше могут устаревать до момента инвалидации. <br> - Не всегда актуальны данные в момент их использования. |
| **По TTL (Time-to-Live)** | - Простота настройки. <br> - Автоматическое удаление устаревших данных. <br> - Удобно для данных с известной продолжительностью жизни. | - Могут быть устаревшие данные в кеше между моментами инвалидации и нового извлечения данных. <br> - Нет чёткого контроля за актуальностью данных в момент запроса. |
